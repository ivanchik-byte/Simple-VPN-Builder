# Анализ стека и концепции: Simple-VPN-Builder

> Документ подготовлен для оценки архитектуры, стека технологий и соответствия бизнес-идее коммерческого VPN-сервиса (поднятие серверов, создание тарифов и продажа доступа пользователям).

## 1. Краткая оценка текущего состояния проекта

1. **Продуманная архитектура**: Четкое разделение на **Control Plane** (мозг, БД, веб-панель, API) и **Node Agent** (легковесные демоны на серверах выхода) через `gRPC` + `mTLS`. Это правильный enterprise-подход, на котором строятся масштабируемые VPN-сервисы (а не монолит на одном VPS).
2. **Документация и спецификация**: [SPEC.md](file:///home/ivan/Projects/Simple-VPN-Builder/SPEC.md) и [PHASES.md](file:///home/ivan/Projects/Simple-VPN-Builder/PHASES.md) прописаны очень детально (редкость для ранних стадий). Четко описаны фазы с 0 по 10.
3. **Схема базы данных ([001_init.up.sql](file:///home/ivan/Projects/Simple-VPN-Builder/migrations/001_init.up.sql))**:
   - Уже заложены таблицы `nodes`, `users`, `plans` (тарифы), `credentials`, `traffic_stats` (почасовой учет трафика), `admins`, `api_keys`, `audit_logs`.
   - Заложена поддержка лимитов трафика (`traffic_limit`, `traffic_used`) и сроков действия (`expires_at`), что критически важно для монетизации.
4. **Protobuf ([agent.proto](file:///home/ivan/Projects/Simple-VPN-Builder/proto/agent/v1/agent.proto))**:
   - Полноценная двунаправленная потоковая схема: регистрация ноды, heartbeat, сбор метрик, пуш конфигураций (`ConfigUpdate`), удаленные команды (`Command`).

### Текущий технический статус (в коде):
- Каркас находится в стадии перехода от Phase 0 к Phase 1.
- В файлах [cmd/control-plane/main.go](file:///home/ivan/Projects/Simple-VPN-Builder/cmd/control-plane/main.go) и [cmd/agent/main.go](file:///home/ivan/Projects/Simple-VPN-Builder/cmd/agent/main.go) объявлены вызовы пакетов (`store`, `auth`, `manager`, `syncer`), которые пока не имеют реализации (заглушки) — это нормально, так как разработка первой фазы идет прямо сейчас.

## 2. Соответствует ли проект твоей идее?

> **Твоя идея**: Человек поднимает свой VPN-сервер для коммерции, создает тарифы/пользователей и продает доступ клиентам.

### Вердикт: **ДА, соответствует на 85-90% по архитектуре**, но требует двух важных акцентов для коммерческого успеха:

1. **Где сходство (100% попадание)**:
   - В модели данных уже есть тарифы (`plans`), пользователи (`users`), учет гигабайтов (`traffic_limit`, `traffic_used`), даты сгорания подписки (`expires_at`).
   - Централизованная панель может управлять десятками серверов в разных странах (Нидерланды, Германия, США, Турция и т.д.).
   - Предусмотрены API ключи для внешних интеграций (`api_keys`).

2. **Что обязательно нужно учесть для реальной коммерции (чего не хватает в чистом MVP)**:
   - **Точка продаж**: Обычные люди не регистрируются через сложные веб-сайты и тем более не ходят в API. В СНГ и ряде других стран **95% продаж коммерческих VPN происходит через Telegram-ботов** (оплата через Telegram Stars, Крипту, СБП/ЮKassa/Cryptomus). Твой Control Plane должен отдавать простой REST API, к которому подключается любой бот.
   - **Блокировки провайдеров (РКН / DPI / TSPU)**: Чистый WireGuard сегодня блокируется почти всеми мобильными операторами и домашними провайдерами в РФ и других странах с цензурой. **Для коммерции протокол VLESS-Reality (или Sing-box/Shadowsocks-2022/AmneziaWG) — это вопрос выживания бизнеса.** Без них клиенты будут массово требовать возврат денег.

## 3. Анализ технологического стека

| Слой | Выбранный стек | Оценка | Рекомендации и нюансы |
|---|---|---|---|
| **Язык бэкенда** | Go 1.23 | **10/10** | Идеальный выбор для сетевого демона, низкое потребление RAM, высокая скорость, отличная работа с gRPC и системными вызовами Linux. |
| **База данных** | PostgreSQL 16 + `pgx/v5` + `sqlc` | **10/10** | `sqlc` генерирует типобезопасный код из чистого SQL. Нет тяжелых ORM-оверхедов. Прекрасная скорость работы с транзакциями и метриками трафика. |
| **Кэш / Очереди** | Redis 7 | **9/10** | Отлично подходит для хранения онлайн-сессий, рейт-лимитинга, временных токенов подписок и Pub/Sub уведомлений. |
| **Связь CP ↔ Agent** | gRPC + mTLS | **10/10** | Лучший стандарт для распределенных систем. Агенты держат постоянный стрим, CP пушит конфиги без задержек. mTLS исключает взлом нод без сертификата. |
| **HTTP API фреймворк** | В `go.mod` стоит Gin, в `SPEC.md` указан Chi + `oapi-codegen` | **7/10** *(Рассинхрон)* | **Важно выбрать что-то одно**: если делаешь генерацию по OpenAPI (`oapi-codegen`), то **Chi** подходит намного лучше и чище, чем Gin. Gin избыточен и тянет лишние зависимости. |
| **Панель управления (Admin UI)** | Go templates + HTMX + Alpine.js | **10/10** | Идеально для соло-разработчика. Не нужно писать отдельный тяжелый фронтенд на React/Vue/Node.js. Быстро, просто деплоится в одном бинарнике. |
| **Сетевые протоколы (Агент)** | WireGuard (netlink/kernel) + Xray (VLESS-Reality) | **8.5/10** | WireGuard хорош для чистых сетей, но уязвим к DPI. Xray закрывает обход блокировок. **Альтернатива/Улучшение**: присмотреться к **Sing-box** вместо Xray-core (Sing-box написан на Go, легче интегрируется как библиотека и потребляет меньше памяти). |
| **Формат выдачи клиенту** | Подписочные ссылки (Base64 / JSON) | **10/10** | Единая ссылка подписки (`/sub/{token}`) позволяет клиенту вставить ее один раз в приложение и получать обновления серверов автоматически. |

## 4. Как это будет работать в жизни: Сценарии использования

### Сценарий А: Разработчик / Владелец сервиса (Администратор)
1. **Развертывание Control Plane**:
   - Покупает 1 VPS (например, за $3-5/мес под панель).
   - Запускает `docker-compose up -d` (Postgres, Redis, Control Plane).
2. **Подключение серверов выхода (Exit Nodes)**:
   - Покупает VPS в разных локациях (Франкфурт, Амстердам, Хельсинки).
   - На каждом сервере выполняет одну команду (установка агента):
     ```bash
     curl -sSL https://vpn.my-service.com/install-agent.sh | bash -s -- --token=NODE_REG_TOKEN
     ```
   - Агент генерирует ключи, связывается с CP по gRPC (mTLS), в панели появляется зеленый статус "Node Online".
3. **Настройка монетизации**:
   - В админке создает планы:
     - *Тариф "Базовый"*: $2/мес, 50 GB, 2 устройства, локации: Нидерланды.
     - *Тариф "PRO"*: $5/мес, Безлимит, 5 устройств, все локации.
4. **Подключение продаж**:
   - Создает API Key в админке.
   - Подключает свой Telegram-бот (на Python / Go / Node.js) к REST API Simple-VPN-Builder.

---

### Сценарий Б: Обычный покупатель (Конечный пользователь)
1. Пользователь заходит в Telegram-бот (или на веб-сайт сервиса).
2. Выбирает тариф (например, "1 месяц — 300 руб") и оплачивает (карта, СБП, крипта).
3. Бот вызывает REST API панели: `POST /api/v1/users` с выбранным `plan_id`.
4. Бот выдает пользователю персональную **ссылку на подписку**:
   `https://vpn.my-service.com/sub/c8f2a49b-7e61...`
   или QR-код.
5. **Подключение на телефоне / ПК**:
   - Пользователь скачивает приложение:
     - iOS: **Happ**, **Streisand**, **V2Box**, **Shadowrocket**, **Amnezia**
     - Android: **v2rayNG**, **Happ**, **NekoBox**
     - Windows / Mac: **Hiddify**, **v2rayN**, **Sing-box**
   - Вставляет ссылку в приложение. Приложение автоматически подгружает все серверы сервиса.
   - Нажимает кнопку «Включить».
6. **Контроль и списание**:
   - Агент каждые 30 секунд отправляет на CP объем скачанных байт.
   - Если трафик превышен или прошел месяц: статус пользователя меняется на `expired/suspended`.
   - CP пушит агентам команду удалить или заблокировать UUID/ключ пользователя.
   - VPN у пользователя отключается до следующей оплаты.

## 5. Что нужно подправить в стеке и планах?

### 1. Выбрать между Chi и Gin
В `go.mod` подключен `gin-gonic/gin`, а в `SPEC.md` и `PHASES.md` запланирован `go-chi/chi` + `oapi-codegen`.
- **Рекомендация**: Оставить **Chi**. Для сервисов с кодогенерацией OpenAPI и middleware-цепочками Chi стандарт де-факто в Go. Gin избыточен и тянет лишние зависимости.

### 2. Приоритет протоколов для коммерции: VLESS-Reality на 1-е место
- Если продукт делается на продажу (особенно на русскоязычный рынок), то **WireGuard заблокируют у 80% клиентов**.
- В плане WireGuard идет Phase 5, а Xray — Phase 6.
- **Рекомендация**: Если цель быстро продавать — протокол VLESS-Reality (через Xray или Sing-box) должен быть ключевым флагманом. Либо предусмотреть поддержку **AmneziaWG** (форк WireGuard с обфускацией заголовков `Jc/Jmin/Jmax/S1/S2/H1..H4`), который сейчас активно используется для обхода блокировок.

### 3. Sing-box вместо Xray-core (на подумать)
- `Xray-core` — отличная штука, но написан своеобразно, много легаси.
- `sing-box` — современное ядро от SagerNet, написано чисто на Go, имеет нативную модульную архитектуру, потребляет меньше RAM и поддерживает все протоколы (VLESS, Reality, ShadowTLS, TUIC, Hysteria2, WireGuard).
- Проекты уровня Marzban переходят на sing-box. Для Go-проекта его встраивать даже удобнее.

### 4. Добавить интерфейс Webhooks / Telegram Bot интеграции
В Phase 3 или отдельной фазе добавить:
- Webhooks на события: `user.expired`, `user.traffic_warning_80`, `node.down`.
- Готовый пример (example) простого Telegram-бота на Go или Python для продажи подписок через этот API.

Стек выбран отлично. После завершения Phase 1 (Data Layer & Repos) архитектура будет готова к реализации бизнес-логики.
